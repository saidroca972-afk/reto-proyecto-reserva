# Constitución del backend

## 1. Nombre del proyecto

**Sistema de reservas de mesas para restaurante — Backend**

El backend proporcionará una API REST para autenticar al administrador y gestionar las reservas del restaurante.

La base de datos utilizada será `reservadb`, definida en los scripts SQL existentes dentro de la carpeta `db`.

## 2. Objetivo

Construir un backend seguro, validado y preparado para desplegarse en Vercel, que permita:

1. Iniciar sesión como administrador.
2. Cerrar sesión como administrador.
3. Registrar una reserva.
4. Actualizar una reserva.
5. Listar todas las reservas.
6. Listar reservas aplicando filtros.

## 3. Tecnologías

| Área | Tecnología | Uso |
|---|---|---|
| Lenguaje | TypeScript | Tipado estático y desarrollo del backend |
| Framework HTTP | Hono.js | Construcción de la API REST |
| Autenticación | JWT | Identificación del administrador autenticado |
| Hash de contraseñas | bcrypt | Encriptación irreversible de contraseñas con 8 saltos |
| Validación | Zod | Validación de cuerpos, parámetros y filtros |
| Base de datos | MySQL/MariaDB | Persistencia de administradores y reservas |
| Cliente de base de datos | mysql2 | Conexión y ejecución de consultas SQL |
| Despliegue | Vercel | Ejecución de la API como Functions |

### Criterio para JWT

Se utilizará `jose` para firmar y verificar los JWT, porque ofrece una implementación compatible con APIs Web y Node.js.

### Criterio para bcrypt

Se utilizará `bcrypt` con ocho saltos:

```ts
bcrypt.hash(contrasena, 8)
```

El backend deberá utilizar el runtime **Node.js** en Vercel. No se utilizará Edge Runtime, debido a que `bcrypt` depende de componentes nativos de Node.js.

## 4. Compatibilidad con Hono y Vercel

Hono está basado en estándares web y ofrece soporte para Vercel. La documentación oficial indica que una aplicación Hono puede desplegarse en Vercel con configuración mínima o cero configuración.

Referencias oficiales:

- [Hono — Vercel](https://hono.dev/docs/getting-started/vercel)
- [Vercel — Hono](https://vercel.com/docs/frameworks/backend/hono)

### Reglas de integración

- La instancia de Hono deberá exportarse como `default`.
- El punto de entrada recomendado será `src/index.ts`.
- La aplicación se ejecutará localmente con `vercel dev`.
- Las rutas serán convertidas por Vercel en Functions.
- Las credenciales y secretos se configurarán mediante variables de entorno.
- La conexión a MySQL deberá utilizar una base de datos externa accesible desde Vercel.
- No se almacenará información mutable en el sistema de archivos local de Vercel.

Ejemplo conceptual del punto de entrada:

```ts
import { Hono } from 'hono'

const app = new Hono()

app.get('/api/health', (c) => {
  return c.json({ status: 'ok' })
})

export default app
```

## 5. Arquitectura propuesta

Se utilizará una arquitectura de **tres capas**, adaptada a una API REST:

```text
src/
├── index.ts
├── app.ts
├── config/
│   ├── env.ts
│   └── database.ts
├── routes/
│   ├── auth.routes.ts
│   └── reservas.routes.ts
├── controllers/
│   ├── auth.controller.ts
│   └── reservas.controller.ts
├── services/
│   ├── auth.service.ts
│   └── reservas.service.ts
├── repositories/
│   ├── administrador.repository.ts
│   └── reservas.repository.ts
├── middlewares/
│   ├── auth.middleware.ts
│   ├── error.middleware.ts
│   └── validation.middleware.ts
├── schemas/
│   ├── auth.schema.ts
│   └── reservas.schema.ts
├── types/
│   ├── auth.types.ts
│   └── reservas.types.ts
└── utils/
    ├── jwt.ts
    └── password.ts
```

### Capa de rutas

Define los métodos HTTP, las rutas y la composición de middlewares. No debe contener lógica de negocio ni consultas SQL.

### Capa de controladores

Interpreta la petición HTTP, obtiene los datos validados, invoca los servicios y construye la respuesta HTTP.

### Capa de servicios

Contiene las reglas de negocio, incluyendo autenticación, generación de tokens y operaciones sobre reservas.

### Capa de repositorios

Encapsula el acceso a MySQL. Los servicios no deberán ejecutar SQL directamente.

### Middlewares transversales

- Validación de entradas con Zod.
- Verificación de JWT.
- Manejo centralizado de errores.
- CORS.
- Registro de peticiones.

## 6. Modelo de datos

### Administrador

Campos existentes:

- `Identificador`
- `Usuario`
- `Contrasena`

La contraseña se almacenará como hash bcrypt en el backend. El valor sin encriptar solo se aceptará como entrada durante el inicio de sesión y nunca se guardará directamente.

### tablaReserva

Campos existentes:

- `Identificador`
- `NombreCliente`
- `NumeroCliente`
- `EstadoPedido`
- `NumeroMesa`
- `FechaReserva`

Los estados válidos serán exactamente:

```text
Disponible
Cancelado
```

## 7. Variables de entorno

```env
NODE_ENV=development
DATABASE_URL=mysql://usuario:contrasena@host:3306/reservadb
JWT_SECRET=clave-secreta-larga-y-segura
JWT_EXPIRES_IN=2h
BCRYPT_SALT_ROUNDS=8
CORS_ORIGIN=http://localhost:3000
```

Reglas:

- El archivo `.env` no debe subirse al repositorio.
- `JWT_SECRET` deberá ser suficientemente largo y aleatorio.
- En Vercel, las variables deberán configurarse para Development, Preview y Production según corresponda.
- Nunca se devolverá la contraseña ni su hash en las respuestas de la API.

## 8. API REST

### Inicio de sesión

```http
POST /api/auth/login
```

Entrada:

```json
{
  "usuario": "sabinofc",
  "contrasena": "123456"
}
```

Respuesta exitosa:

```json
{
  "message": "Inicio de sesión exitoso",
  "token": "jwt"
}
```

### Cerrar sesión

```http
POST /api/auth/logout
Authorization: Bearer <token>
```

El cliente deberá eliminar el JWT después de recibir una respuesta exitosa.

Como el JWT es stateless, el cierre de sesión no invalida por sí solo un token ya emitido. Si posteriormente se requiere revocación inmediata, se deberá añadir un mecanismo de sesiones o lista de tokens revocados.

### Registrar reserva

```http
POST /api/reservas
Authorization: Bearer <token>
```

Ejemplo:

```json
{
  "nombreCliente": "Ana Martinez",
  "numeroCliente": "5551234567",
  "estadoPedido": "Disponible",
  "numeroMesa": 1,
  "fechaReserva": "2026-10-01T12:30:00"
}
```

### Actualizar reserva

```http
PUT /api/reservas/:id
Authorization: Bearer <token>
```

### Listar reservas

```http
GET /api/reservas
Authorization: Bearer <token>
```

### Listar reservas filtradas

```http
GET /api/reservas?estado=Disponible
Authorization: Bearer <token>
```

Filtros previstos:

- `estado`
- `numeroMesa`
- `nombreCliente`
- `fechaDesde`
- `fechaHasta`

## 9. Validaciones con Zod

Se crearán esquemas independientes para:

- Inicio de sesión.
- Registro de reservas.
- Actualización de reservas.
- Parámetros de ruta.
- Filtros de listado.

Reglas mínimas:

- `usuario`: obligatorio, máximo 15 caracteres.
- `contrasena`: obligatoria en el login.
- `nombreCliente`: obligatorio.
- `numeroCliente`: cadena de números telefónicos válida.
- `estadoPedido`: únicamente `Disponible` o `Cancelado`.
- `numeroMesa`: entero positivo.
- `fechaReserva`: fecha válida; si se omite, se utilizará la fecha y hora por defecto de la base de datos.

## 10. Respuestas HTTP

| Código | Uso |
|---|---|
| 200 | Operación exitosa |
| 201 | Recurso creado |
| 400 | Datos inválidos |
| 401 | Token ausente, inválido o credenciales incorrectas |
| 404 | Recurso no encontrado |
| 409 | Conflicto de datos |
| 500 | Error interno del servidor |

Formato de error:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Los datos enviados no son válidos",
    "details": []
  }
}
```

## 11. Fases de implementación

### Fase 1: Inicialización del proyecto

- Crear el proyecto TypeScript.
- Configurar `package.json` y `tsconfig.json`.
- Instalar dependencias.
- Crear `src/index.ts` y `src/app.ts`.
- Configurar scripts de desarrollo, pruebas y producción.
- Configurar el runtime Node.js para Vercel.

### Fase 2: Infraestructura y configuración

- Implementar lectura y validación de variables de entorno.
- Crear el pool de conexión MySQL.
- Configurar CORS, logger y manejo global de errores.
- Crear endpoint de salud `/api/health`.

### Fase 3: Validación y tipos

- Definir interfaces de administrador y reserva.
- Crear esquemas Zod.
- Implementar middleware de validación.
- Estandarizar respuestas y errores.

### Fase 4: Autenticación

- Crear repositorio de administrador.
- Implementar comparación con bcrypt.
- Implementar generación y verificación de JWT.
- Implementar `POST /api/auth/login`.
- Implementar `POST /api/auth/logout`.
- Proteger las rutas de reservas.

### Fase 5: Gestión de reservas

- Crear repositorio de reservas.
- Implementar registro de reservas.
- Implementar actualización de reservas.
- Implementar listado general.
- Implementar filtros por estado, mesa, cliente y rango de fechas.

### Fase 6: Pruebas

- Probar credenciales válidas e inválidas.
- Probar acceso sin token y con token inválido.
- Probar creación y actualización de reservas.
- Probar filtros.
- Probar datos incompletos o inválidos.
- Probar errores de conexión y consultas a la base de datos.

### Fase 7: Seguridad y calidad

- Confirmar que nunca se devuelvan contraseñas.
- Revisar expiración y firma de JWT.
- Verificar que todas las rutas sensibles requieran autenticación.
- Configurar ESLint y Prettier.
- Revisar consultas parametrizadas para evitar inyección SQL.

### Fase 8: Despliegue

- Vincular el proyecto con Vercel.
- Configurar variables de entorno.
- Verificar la ejecución local con `vercel dev`.
- Desplegar una versión Preview.
- Validar la conexión con MySQL.
- Desplegar a Production.

## 12. Criterios de aceptación

- El backend inicia correctamente con TypeScript y Hono.
- La aplicación es compatible con Vercel usando Node.js Runtime.
- El administrador puede iniciar sesión con credenciales válidas.
- Las contraseñas se procesan con bcrypt usando 8 saltos.
- Las rutas de reservas rechazan peticiones sin JWT válido.
- Se pueden crear, actualizar y consultar reservas.
- Los filtros funcionan correctamente.
- Los estados inválidos son rechazados por Zod y por la base de datos.
- Las respuestas no exponen contraseñas ni información sensible.
- Los errores tienen un formato uniforme.
- El proyecto puede ejecutarse localmente y desplegarse en Vercel.
